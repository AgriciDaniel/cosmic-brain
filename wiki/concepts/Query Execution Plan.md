# Query Execution Plan

The query optimizer's chosen strategy for satisfying a SQL query — which access paths (scan vs. seek), join algorithms, and operator order it will use. Interpreting execution plans is the primary way to identify why a query is slow and which index or rewrite would fix it.

## Two Plan Types

- **Estimated Execution Plan** — generated by the optimizer without running the query. Shows the projected steps and estimated row counts/costs. No runtime statistics. Useful for checking a plan before running an expensive or destructive query.
- **Actual Execution Plan** — generated after the query runs. Includes everything the estimated plan has, plus actual runtime statistics (actual rows vs. estimated rows), warnings (e.g., implicit conversions, missing indexes, spills to tempdb), and the steps as actually executed.

In SQL Server Management Studio, both are toggled from the Query menu toolbar ("Include Actual Execution Plan" / "Display Estimated Execution Plan").

## Reading Convention

Graphical execution plans read **top to bottom, and right to left**. The rightmost, bottommost operators execute first (typically table/index scans or seeks); results flow left and up through join/filter/sort operators toward the final SELECT operator at the top-left.

## Why Estimated vs. Actual Matters

A large gap between the optimizer's *estimated* row count and the *actual* row count at a given operator is one of the strongest signals of stale statistics or a cardinality-estimation problem — the optimizer picked a plan that was correct for its estimate but wrong for reality (e.g., chose a nested loop join expecting 10 rows, got 10 million). This is the same failure mode documented in `.raw/CLAUDE.md`'s indexing rules: "stale statistics — always run `ANALYZE table_name` after bulk inserts/deletes" (PostgreSQL equivalent: `UPDATE STATISTICS` / auto-stats in SQL Server). See [[SQL Server Statistics and Cardinality Estimation]] for the full statistics/histogram mechanics behind this.

## Seek vs. Scan: The Core Myth

The single most repeated correction across Brent Ozar Unlimited's "How to Think Like the Engine" series ([[how-to-think-like-the-engine-part-1]] and its sibling sessions, [[how-to-think-like-the-sql-server-all-demo-edition]], [[how-to-think-like-the-sql-server-engine-part-2]]):

- **An Index Seek does NOT mean the operator is lightweight or fast.** It only means "jump to a starting point in the index and read from there." How much gets read after the jump depends entirely on the predicate and data distribution.
- **An Index/Table Scan does NOT mean the operator is slow.** It means "start reading from one end." This can be highly efficient — e.g., `SELECT TOP 10 ... ORDER BY indexed_col` scans from one end and stops after 10 rows.
- **Demonstrated live, repeatedly**: seeking to a very early value (e.g., the year 1800) in a date-ordered index still reads almost the entire table if most rows have later dates — the seek finds its starting point instantly, but then has to scan forward through nearly everything anyway. The operator label ("Seek" vs "Scan") tells you *how the read started*, not *how much was read* or *how fast the query was*. Always check actual/estimated row counts and cost, not the operator name, to judge a plan.

## Key Lookup

When a non-clustered index doesn't contain every column a query needs, SQL Server performs a **Key Lookup** (or RID Lookup for a heap) back into the clustered index to retrieve the missing columns.

> [!important] The Key Lookup executes **once per matching row returned by the seek/scan**, not once total. This is a commonly misunderstood cost driver: a plan showing "Index Seek → Key Lookup" that looks cheap for 1 row becomes very expensive for 100,000 matching rows, because the Key Lookup runs 100,000 times, each a small random I/O.

**Covering index**: a non-clustered index that includes every column the query needs (via key or `INCLUDE` columns), eliminating the Key Lookup entirely. See [[Database Indexing]] for the SQL Server clustered/non-clustered index model and INCLUDE-vs-KEY column guidance this depends on.

## Tipping Point

The cost-based threshold at which SQL Server abandons an Index-Seek-plus-Key-Lookup plan in favor of a full table/clustered-index scan.

- Driven by the *estimated* row count from statistics (see [[SQL Server Statistics and Cardinality Estimation]]) — decided before execution, not from actual data.
- Demonstrated as surprisingly low in the source material — sometimes under **0.3% of a table's rows**. Intuition that "an index should help unless we're reading most of the table" is wrong by an order of magnitude; the optimizer tips over to a scan far earlier than most developers expect, because each Key Lookup is a separate random I/O and those add up fast even at low row counts.
- Because the tipping point is driven by the *estimate*, stale statistics can cause the optimizer to tip the wrong way in either direction (scan when a seek+lookup would've been cheaper, or vice versa).

## Estimated Subtree Cost ("Query Bucks")

**Estimated Subtree Cost** — nicknamed "query bucks" or "query cents" by Kendra Little (MCM, Redgate) — is the optimizer's internal cost number for a plan or sub-plan, shown in the execution plan's operator tooltips/properties.

- Historically calibrated against CPU/IO benchmarks run on a specific old Dell desktop machine (per Microsoft's original SQL Server optimizer design). Today it is a **unitless heuristic** with no direct relationship to wall-clock time or real hardware performance.
- Useful **only** for what the optimizer uses it for: comparing candidate plans against each other *before execution*, to pick the cheapest-looking one. Not meaningful for comparing the actual performance of two different queries, or across two different servers/hardware generations.

## Optimization Levels and Parallelism

- **Trivial vs. Full optimization**: SQL Server skips full cost-based plan search for trivially simple queries (e.g., a single-table query with no join/index choices to make), going straight to a "trivial" plan. Full optimization kicks in once there's a real decision space to search (multiple indexes, joins, etc.).
- **Cost Threshold for Parallelism** — server-level setting, default **5 query bucks**. Once a plan's estimated cost exceeds this threshold, SQL Server considers a parallel (multi-thread) version of the plan. The parallelism icon in a graphical plan is nicknamed **"racing stripes"** (Erik Darling).

## Memory Grants

SQL Server pre-allocates memory (measured in KB) for sort and hash operations **before** the query executes, sized from the optimizer's row-count/width estimates — not from what actually happens at runtime.

- If the estimate is too low, the operation **spills to tempdb** mid-execution — the "public toilet" analogy used across the source material (also applied to RCSI/Snapshot Isolation's tempdb row-versioning, see [[SQL Server Locking, Blocking, and Concurrency Control]]).
- Spills are visible as warnings on Sort/Hash Match operators in the actual execution plan, and are one of the clearest actionable signals that statistics or cardinality estimates need attention.

## SQL Server Never Caches Query Results

Unlike Oracle (which offers result-set caching), SQL Server **only caches data pages**, never the results of a completed query. Re-running the identical read-only query (`GO 10`, `GO 50`, `GO 100` in SSMS) redoes the full CPU work every single execution, even with no data changes. This is explained in the source material as a byproduct of SQL Server's cheaper licensing model (SQL Server Enterprise ≈ $7,000/core vs. Oracle Enterprise ≈ $47,000/core) — a practical implication is that sorting and other expensive operators are often better pushed to the application tier if the same result set will be requested repeatedly. `DBCC FREEPROCCACHE` clears cached *execution plans* (not data pages) and is a demo-only tool, never for production use.

# Wait UX - Fluent 2 Design System

## Overview

How systems present themselves during processing/loading/data delays. "These moments, if not handled well, can lead to frustration, abandonment, or loss of trust." Across both Copilot AI tools and traditional M365.

## Core Principles

**Clear Communication** — descriptive labels ("Uploading photo…", "Loading dashboard…"). Determinate progress preferred; indeterminate spinners only for brief waits.

**Perceived Performance Optimization** — visual feedback reduces felt-delay. Shimmer, skeletons, micro-interactions. "For short waits under one second, don't show any animation — doing so may confuse users." Never show blank/static.

**Contextual Consistency** — keep users in current view. One progress notification, not multiple spinners.

## Visual Patterns

- **Spinner** — short indeterminate waits < 3s; present-participle + ellipsis ("Loading…")
- **Progress Bar** — measurable longer waits; task label above, status below ("Uploading file…" / "30% complete – about 20 seconds remaining")
- **Skeleton Screens** — content rendering delays; Copilot uses gradient shimmer
- **Progress Toast** — background processes affecting current work
- **Morse Code Animation** — Copilot scenarios; mimics typing without anthropomorphizing
- **Pulsing Dot** — Chain of Thought workflows

## Timing Guidance

| Wait | Approach |
|------|----------|
| < 1s | No indicator |
| 1–3s | Spinner |
| > 3s | Progress bar or reassurance message |
| AI chat | Immediate response indicators |

## Content Patterns

- **Labeling**: present-participle ongoing ("Uploading file…"), past tense complete ("File uploaded"). Avoid passive ("File is being uploaded").
- **Conciseness**: single phrase
- **Expectation setting**: time estimates for non-AI; activity indicators for AI

## Accessibility

ARIA must announce state changes via `role="status"`. Ellipses need nonbreaking spaces for screen readers.
